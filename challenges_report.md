# Engineering Challenges in Building a Fault-Tolerant, Security-Hardened Linux-Capable RISC-V Processor on a 1mm² Die

## Feature Categories

We organize the features we are implementing into seven categories, which we reference throughout the rest of this section rather than individual implementations.

**Error Correction** covers all ECC and parity code mechanisms applied to internal structures: cache SRAMs, the register file, CSR registers, pipeline registers, and the off-chip memory bus.

**Redundancy** covers physical and logical duplication of critical state and logic, including TMR-style protection of control signals and registers, with instances placed with spatial separation to resist localized fault injection.

**Re-execution** covers fault detection through duplicated execution and output comparison; this includes a shadow execution pipeline that simultaneously serves as our execution unit integrity checker, a hardware thread that runs behind the main pipeline to verify load and store consistency against the cache and commit state, and periodic insertion of instructions with known expected outputs that verify the processor is producing correct results at runtime.

**Architectural State Hardening** covers protection of privilege-critical registers and control state against physical tampering, specifically targeting the CSR file, interrupt controller state, and privilege mode registers as the primary attack surface for glitch-based privilege escalation.

**Environmental and Power Hardening** covers circuits that detect and respond to out-of-bounds supply conditions, protecting against events that could corrupt processor state or cause undefined behavior.

**Security Controls** covers hardware entropy generation for cryptographic and runtime security applications, and debug interface locking to prevent adversarial use of JTAG access as an attack vector.

**Validation Infrastructure** covers the synthesis, simulation, FPGA boot, co-simulation, and fuzzing tooling needed to verify that all of the above mechanisms work correctly across the conditions we care about.

## The Area Constraint

At 65nm TSMC with 1mm² of die area, we are not working with much margin for high-area features. A Linux-capable CVW configuration (RV64GC, Sv39 MMU, L1 I/D caches, CLINT, PLIC, FPU) is already a large design. At 65nm, a 6T SRAM bit cell is around 0.57μm², meaning a pair of 16KB L1 caches already takes up something like 150,000 to 200,000 μm² in bit cell area alone, before adding tag arrays, column muxes, or any periphery. The digital logic for the core, MMU, and peripherals is another large chunk on top of that. By the time we have a functional Linux core, we are already in a regime where adding the aformentioned features means cutting or shrinking something else.

What makes this harder than a typical area budget is that the cost of each feature category is not known precisely until we synthesize. Error correction mechanisms look manageable individually on paper; but they compound across every structure we apply them to, and the choice of how aggressively to apply them (whether to use parity or a full SECDED code, which structures to cover, whether to protect pipeline registers or only architectural register boundaries) directly drives the area outcome. Re-execution is the most expensive category we are adding; it requires duplicating execution logic and maintaining additional buffering and forwarding infrastructure to keep the re-executing path consistent with the main pipeline. Redundancy adds overhead wherever it is applied; and environmental and power hardening mechanisms are analog blocks with footprints that are disproportionately large relative to equivalent digital logic at this node. Security controls are relatively cheap, but they still contribute to the total.

None of these costs are fixed at design time. Area numbers come back from synthesis, and decisions get revisited every iteration: which structures get full error correction versus parity, how aggressively we apply redundancy to architectural state, whether re-execution covers a full pipeline instance or a reduced subset given area feedback. These are not one-time decisions; they get re-evaluated every time a synthesis run finishes. And at the scale of a full Linux-capable core with all these modifications, those runs take hours. If synthesis is run ad hoc, area overruns surface late, meaning they are the most expensive to fix. The synthesis flow has to be treated as actual infrastructure from the start: automated, run regularly, and tracked across every feature addition alongside the RTL development.

## Physical Design

Even if the total gate count fits within 1mm², getting everything placed and routed correctly is its own problem. The clearest case is our redundancy mechanisms. If we use physical redundancy to protect against fault injection, the redundant instances need spatial separation, because a localized EM pulse or power glitch that hits both copies simultaneously defeats the redundancy entirely. The PnR tool has no native understanding of this; it has to be expressed as explicit placement constraints or floorplan blockages. Those constraints then have to be satisfied alongside timing, routing density, and the need to keep related logic close enough that critical paths do not blow up. On a 1mm² die, explicitly separating redundant instances while simultaneously keeping the rest of the design compact is a real constraint-satisfaction problem with no guaranteed clean solution.

Error correction mechanisms add yet another constraint. The check logic for a given structure ideally sits co-located with that structure, adding extra area on top of the normal design that we have to place and route. Given the amount of logic that is uncertain to fit, we need to think of an efficient way to do both proper area estimations alongside writing RTL.

## The I/O Ring Bottleneck

We have at most 53 I/O rings total. A standard RISC-V cacheline is 64 bytes, or 512 bits. After allocating for JTAG (5 signals), power and ground (8 to 12 rings), clock and reset (2 to 3), and other necessary I/O, we are left with somewhere around 30 to 35 rings for memory. That is not enough to transfer a cacheline in a single cycle.

We are still working through what the right memory interface looks like. The general direction is a serialized burst protocol with a narrow data bus that fills a cacheline over multiple cycles. But even that leaves real questions open: what protocol, how dirty write-back evictions are handled (the same serialization penalty applies as for a fill), and how our error correction mechanisms layer on top of the bus-level transfers. A narrow bus fits reasonably well with error correction at the bus level, since error correction on narrow data words is well understood and adds relatively few extra signals. But error correction at the bus level is a separate problem from error correction inside the cache SRAMs, meaning both have to be addressed independently.

The larger issue is that every cache miss now pays a multiplied fill penalty. For a Linux workload, cache miss rate drives a large fraction of effective throughput, and the bus width is a hard ceiling on memory performance regardless of how fast the core logic runs. This also has direct implications for our validation infrastructure. If the FPGA build uses a wider memory interface for convenience, the cache fill timing will be fundamentally different from what silicon sees; any performance-sensitive fault injection scenario will not transfer, and the FPGA run loses some validity as a proxy for the taped-out chip. While the end goal of this tape-out is an exploration into security-focused micro-architecture and not necessarily optimal performace, trade-offs between performance and complexity need to be deeply evaluated for our tape-out to show interesting results.

## Verifying Linux Correctness

Linux boot is somewhere between one and ten billion instructions. A full RTL simulation in Verilator for a core this complex already takes hours per boot run without any fault injection or co-simulation overhead. The signal we use to measure progress is UART output that notifies us whether the kernel reaches specific boot milestones, whether userspace initializes correctly. That is a coarse signal; it tells us the system is mostly working, but gives no instruction-level visibility into whether a specific error correction event fired correctly, whether our re-execution mechanisms caught an injected fault, or whether architectural state hardening triggered when it should have.

This pushes alot of the fault injection and recovery validation onto the FPGA. The FPGA can boot Linux in tens of seconds to minutes at realistic clock frequencies, which is workable for testing purposes. But making the FPGA a meaningful validation artifact means building fault injection into the FPGA build itself: RTL that can inject bit flips into specific structures on a cycle-accurate schedule, with a control interface and a log of what was injected and how the core responded. That fault injection RTL needs its own verification; a bug in the injection mechanism could make recovery look correct when it is not, giving false confidence to the effectiveness of our tape-out.

Our security controls create a validation lifecycle problem on top of this. FPGA testing requires JTAG visibility: the ability to inject faults on command, observe internal state, and log responses. Once debug locking is engaged, that access is gone. The validation flow has to be structured so that access control hardening is tested last, or the design needs a secure re-enable mechanism that is itself hardened against the same physical threat model. Either way, the interaction between our security controls and the rest of the validation infrastructure has to be planned upfront, not figured out after the RTL is otherwise done.

## Timing Closure

Adding logic to established critical paths matters. Error correction decode logic on cache read output sits directly on the load-use latency path. Architectural state hardening checks sit in the execute stage. Re-execution mechanisms introduce new forwarding and buffering paths that the base CVW pipeline was not designed for. Any one of these can push a path over timing.

That said, at 65nm targeting the clock frequencies needed for practical Linux boot, the margins are not as thin as they would be at an advanced node. The bigger risk is missing timing narrowly because a late-added feature closes off the last bit of slack on a path that was already close, and that only shows up during PnR. The same discipline that applies to area tracking applies here: critical paths need to be tracked across every synthesis iteration so timing problems surface when there is still time to fix them. While performance, as mentioned previously, is not the primary focus of this tape-out, we want to still tape-out this processor at a reasonable clock frequency.

## Cutting CVW Down to Fit

CVW was built as a highly parameterizable RV64GC core. As a result, the configuration space is large: cache sizes, MMU modes, privilege support levels, FPU, debug module, peripheral controllers. The default Linux-capable configuration includes things that may not all be necessary for this tapeout. Identifying what can actually be removed or reduced without breaking Linux boot, and doing it safely is harder than it sounds.

CVW's parameters are deeply interconnected. Changing cache geometry affects how the MMU handles page table walks. Modifying peripheral support changes what device drivers Linux can use during boot. Some parameters, if wrong, do not cause a synthesis error; they produce RTL that simulates fine for simple tests but breaks under a real Linux workload. The only reliable way to know whether a configuration reduction is safe is to actually boot Linux with it, which brings back the hours-long simulation problem.

Adding our feature categories makes this harder because several of them require modifying CVW's internal structures, not just wrapping around them. Our architectural state hardening requires understanding exactly how CVW implements reads and writes to privilege-critical registers and where those values live in the RTL before we can safely add protection logic. Our re-execution mechanisms have to tap into the CVW pipeline at specific points, and those internal interfaces were not documented for external modification. Error correction on register file reads has to integrate with CVW's existing forwarding network, which was not designed to carry check bits or correction signals alongside data. Each of these is a case where a large, complex codebase has to be understood deeply before it can be safely changed; a wrong assumption produces a bug that only surfaces during Linux boot, hours into simulation.

## The Mechanisms Do Not Compose Cleanly

Each of our feature categories was designed against a specific threat model. Their interactions create failure modes that none of them individually handles.

The clearest case involves error correction and re-execution operating on the same data path. If error correction corrects a fault before a value reaches the execution stage, both the main pipeline and the re-execution path receive the corrected value; they agree, the divergence detector sees nothing, and the correction happens without raising any flags. That is correct behavior for a soft error, but it means our re-execution mechanisms have zero visibility into faults that error correction handles. Error correction has to be the complete solution for that fault class, and the recovery logic has to correctly attribute the event to the error correction layer rather than treating pipeline agreement as a signal that nothing happened.

Re-execution consistency checking has a timing problem. The re-executing path runs behind the main pipeline and issues memory accesses to verify what the main pipeline observed. But if a write-back or eviction happens in the intervening window, the re-executing path sees updated data; that is a spurious divergence that does not indicate any real fault. Distinguishing that from an actual consistency failure requires tracking the memory access window carefully, which adds logic and another surface for bugs.

Architectural state hardening protects privilege-critical register values. But a glitch that corrupts privilege mode state does not necessarily corrupt an execution unit result; it changes what instructions are architecturally permitted. Our re-execution mechanism checks execution unit outputs and does not monitor privilege state, meaning a successful glitch that forces a privilege transition without going through a normal register write path would not be caught by execution comparison. Privilege mode state needs its own separate protection, independent of execution unit checking.

The fault accounting state written when our execution unit checker detects a failing unit is a new attack surface if it is writable by software; it also has to be included in our architectural state hardening scheme. That means the fault detection infrastructure and the state hardening infrastructure are not independent and have to be co-designed. The full recovery hierarchy, from silent correction through pipeline re-execution through unit disabling through trap or reset, also has to interact correctly with the OS; the kernel code for handling these events is part of the correctness surface that needs verification, not just the hardware.

## The Validation Infrastructure

Everything above needs to be verified, and the validation infrastructure for a Linux-capable processor with fault injection, co-simulation, runtime instruction verification, and FPGA-based testing is a non-trivial engineering effort that runs in parallel with the RTL work and competes for the same time.

Our re-execution mechanism that inserts known-result instructions at runtime requires that the co-simulation oracle knows exactly which instructions were inserted and when. The entropy source driving the insertion has to be observable in simulation: either swappable with a deterministic pseudorandom source for simulation purposes, or the inserted instruction stream has to be logged in a way the oracle can replay. If neither is true, co-simulation breaks at every point an inserted instruction appears; the insertion hardware has to be co-designed with the validation approach from the beginning.

Fuzzing for a Linux-capable processor with all of these fault tolerance categories is different from fuzzing a simple RTL block. Standard coverage metrics (line coverage, toggle coverage, FSM state coverage) do not capture whether architectural state hardening is doing anything meaningful, whether re-execution is catching real faults, or whether privilege escalation attempts fail correctly. Effective fuzzing here needs stimulus that specifically targets privilege boundaries, fault injection timing, and recovery scenarios; that requires custom testbench infrastructure, not off-the-shelf tools, and that infrastructure is itself a non-trivial project.

The synthesis flow for area and timing tracking has to be automated and integrated into the development process from the start. If it is run ad hoc, overruns get discovered late. Getting to tapeout on a 1mm² die with this many feature categories requires continuous visibility into actual post-synthesis numbers: not estimates from when a feature was first designed, but real numbers tracked across every iteration of the RTL.

## Development Pipeline as a Response to Simulation Constraints

The simulation bottleneck described above directly constrains how we can develop and integrate features. A single Linux boot in Verilator takes hours, meaning we cannot block feature integration on waiting for full simulation runs to complete before moving to the next feature. Left unaddressed, this would serialize the entire development process and make the timeline infeasible.

Our response is to pipeline the work itself. The immediate priority right now is reducing the CVW configuration to the minimum needed for Linux boot, freeing up as much of the 1mm² budget as possible before we begin integrating the feature categories described above. That work is happening across the team in parallel, so we enter the integration phase with a known baseline that fits rather than discovering overruns mid-integration.

Once we have that baseline, we run three tracks concurrently: writing and integrating new features into the RTL, running synthesis on whatever has been integrated for area estimates, and running simulation on whatever version of the design has been stable long enough to simulate. Synthesis gives us area feedback on features before simulation has finished validating them; simulation runs on whatever stable version of the design exists while the next set of features is being written and synthed.

This means we are making area intensity decisions based on real synthesis numbers rather than waiting for simulation to sign off before committing to a design choice. The tradeoff is that we are sometimes making structural decisions on features that have not yet been fully simulated. That is acceptable given the constraints; the alternative is serializing development on the Linux simulation bottleneck, which is not viable. What this approach does require is that synthesis results are treated as the primary feedback signal for area decisions, and that simulation is structured to catch integration bugs as features stabilize rather than as a gate before any feature work can proceed.
